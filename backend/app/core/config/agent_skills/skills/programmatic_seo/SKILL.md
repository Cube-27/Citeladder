# Programmatic SEO opportunity and pilot

Follow the operating contract. Bind only tools advertised in this run's catalog, and reuse the context package and the evidence already gathered in this chat instead of repeating discovery.

## Outcome and inputs

Decide whether a repeatable page system is warranted and deliver a usable pilot specification, with completed pilot drafts when evidence supports them. A matrix of keyword combinations is not a business opportunity by itself.

Required: verified offer/audience, a candidate repeated buyer task and a usable/licensable source of differentiated data or real functionality. Optional: keyword/SERP patterns, GSC, existing page inventory, AI prompt/source gaps, original data, operational coverage and publishing capabilities.

## Inspect the family before scaling

Examine representative sibling pages side by side, including a strong, ordinary and weak or sparse case when available. Test whether the actual data supports a distinct answer and buyer task, not just a different slug. A saved keyword tag or semantic cluster is not evidence that a page deserves publication. Preserve successful existing destinations and show which candidate combinations were rejected and why. Scope pilot measurement to the selected family rather than attributing whole-site changes to it.

## Workflow

1. **Test the premise.** For each pattern, identify the buyer question, commercial relevance, distinct variables and what each resulting page does that a single comprehensive page cannot. Candidate families can be tools, examples, integrations, locations, comparisons, directories, profiles or other real repeatable needs; do not generate all patterns by default.
2. **Verify truthful coverage.** Confirm each combination represents an actual product, service, integration, location, dataset or decision. A business serving one location cannot claim nationwide local offices. An unbuilt integration is not a working integration. Do not create pages solely to funnel many near-identical searches to the same destination.
3. **Validate demand and existing destinations.** Use matched query/market evidence when available and inspect actual result intent. Low estimated search volume can still support a genuine buyer utility; large aggregate volume does not justify poor-fit pages. Avoid duplicate owned routes and unsupported aggregate volume sums for overlapping variants.
4. **Define the data contract.** Specify fields, source owner, collection rights, public-use permission, update cadence, validators, units and missing/stale-data behavior. Separate facts supplied by the dataset from text that the model may explain. The model must not invent values to make a row publishable.
5. **Describe real per-page value.** Each page must contain useful distinct facts, functionality, examples or decision guidance. Swapped names and a percentage of different prose do not establish value. Design conditional sections from actual row data. Document when a single category page or tool is better than dozens of thin pages.
6. **Create a pilot that tests variation.** Choose a small set covering a typical case, a valuable/high-information case and a difficult sparse/edge case. Three to five pages is a useful default for review, not a search-engine rule. Produce the template/schema and complete drafts only for rows with sufficient verified data. Show why sparse rows fail rather than filling them with generic text.
7. **Design architecture and publication eligibility.** Use the authorized canonical domain and established route family unless a change is approved. Define unique stable URLs, canonical relationships, navigation/hubs, meaningful internal links and sitemap inclusion for eligible pages. Do not claim subfolders universally outrank subdomains. Avoid indexable combinatorial filters or location doorway patterns without real utility.
8. **Set gates before scale.** Each row must pass factual completeness, genuine distinct utility, intent match, conflict/duplicate handling, correct links/metadata and an accountable update owner. Keep failed rows as drafts/excluded from publication. Noindex is not a substitute for creating useful content or a silent sitewide change.
9. **Plan an actual small release and observation.** Publishing requires appropriate authorization/tools. Verify live status, content, canonicals and links after deployment. Observe crawl/index coverage and real useful traffic/engagement/conversions; monitor whether existing pages lose intended query coverage. AI visibility is a separate stable-prompt observation, not guaranteed by page count.
10. **Decide scale/repair/stop.** Scale only if data quality, user value, maintenance capacity and pilot evidence justify it. Slow indexing alone does not prove failure; inspect elapsed time, crawl opportunity, duplication and useful demand. Stop when rows cannot be maintained, fail eligibility, duplicate intent or only simulate local/product coverage.

## Outputs

`programmatic-pilot.md`: pattern, audience/offer, demand evidence, why separate pages are useful, alternatives rejected, data contract, eligibility rules, route/link architecture, pilot selection, acceptance/measurement/stop plan and ownership.

`page-template.md`: deterministic placeholders and conditional sections; title/metadata rules; factual claim/source placement; actual CTA behavior; empty/stale-data behavior; markup only where appropriate.

`pilot-manifest.csv`:

```text
row_id, proposed_url, buyer_task, source_records, unique_value,
required_fields_status, freshness_status, duplicate_intent_check,
publication_eligibility, blocker, template_version, review_owner
```

Create complete pilot drafts when asked and supported. Clearly label empty template fields as implementation variables, not missing facts silently included in public content.

## Validation and boundaries

No automatic bulk publishing, keyword-stuffed variations, fabricated locations or integrations. No universal “60% unique text,” minimum word count or 50-page penalty threshold. Data sources, missing values and maintenance ownership must be explicit. Lack of useful row-level evidence blocks page generation, not a candid rejection/pilot plan. Route technical architecture checks to the Technical health skill, link design to the Internal links skill, and evaluation to the Measure results skill.
