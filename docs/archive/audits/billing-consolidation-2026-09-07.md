### Executive assessment

Do not enable payment collection. The existing architecture has valuable reusable owners (billing account/sponsor links, grants/revocations, resolver, consumable ledger, pending intents, connector protocol, hosted checkout, frontend catalog), but it is not an operational billing system satisfying the requested policy. The most urgent defects are: email-selected privileged signup grants; loss of webhook retries after a committed receipt; current-catalog renewal grants and double grant issuance on revision change; under-specified funded charging; payment-link/payment-ID mismatch; divergent usage arithmetic; permissive no-grant enforcement; workspace/account allowance disagreement; and incomplete expiry/status enforcement.

The requested database-managed tiers/offers/codes, seven-day new-account card-mandate-only trial, operator administration, durable provider-eligibility approvals, refunds/disputes, and scheduled lifecycle reconciliation are **absent**, not features to merely enable. Trial is explicitly rejected today. Merchant eligibility cannot be inferred from code, credentials, documentation, or a test account.

### Concrete findings / evaluated hypotheses

Classification: **NEW** = introduced by this PR relative to origin/main; **EXISTING** = owner/function unchanged on this branch; **GAP** = requested workflow absent. Severity assumes payment features might later be enabled; no claim that anyone was charged or exploited.

#### F01 — NEW critical: privileged account selected by public email, not trusted provisioning

`bootstrap.py:113` identifies a privileged dev login using only `user.email == settings.dev_login_email`; `:92-105,124-134` grants every issuable flag, maximum levels, and 2,147,483,647 counters permanently. Default address is `dev@citeladder.com` (`core/config/__init__.py:102-115`). Public `/auth/register` only disables registration for demo mode (`api/auth.py:43-58`); registration accepts an unclaimed address and provisions grants without email verification (`domain/auth/service.py:51-102`). Therefore in a non-demo deployment where that address is not already claimed, registering it receives privileged grants. No environment/verified-email/trusted-account-ID guard protects this grant path. Existing configured account occupancy can prevent this specific registration but does not make email a privilege boundary.

Accepted root cause: development convenience is implemented inside universal production billing bootstrap. The credential resolver has a `dev_test_login` safety argument defaulting false (`credentials.py:274,304`), but repository search finds no production caller supplying it; do not rely on it to constrain these grants. Fix by explicit audited DB override provisioned through privileged operations, with dev-only seed gated by environment and immutable account identity. Never recognize role from an email string.

#### F02 — NEW high: baseline allowances stack with paid tiers and billing reads mutate

Baseline grants are source `override`, perpetual, never replaced on activation (`bootstrap.py:117-134`). Counter algebra is SUM (`resolver.py:91-102`). A normal Tier 1 buyer therefore resolves **2 projects, 20 prompts, 70 URLs**, not the catalog's 1/10/50; Tier 2 gets 4/40/170. This is not an off-by-one in counting: there are two independent allowance producers with additive semantics. `api/billing.py:235-253` calls `owned_account`, which now always bootstraps and commits (`service.py:340-345`), violating read-only projections. Accepted. Define DB-managed onboarding baseline explicitly and make base entitlements exclusive/replaced (not blindly summed); add-ons remain additive.

#### F03 — NEW high: paid catalog cannot unlock newly gated Content/Growth Agent

New API guards require `content_creation` / `growth_agent` (`api/content.py:91-101,238,344`; `api/agent.py:68-74`). None of the three paid template bundles grant them (`billing_catalog.py:360-431`). Only configured dev/explicit override can get these flags. Thus buying a currently marketed tier cannot unlock those controls even with healthy provider credentials. Accepted configuration/enforcement mismatch, not a reason to remove the backend gates. Approved DB capability bundles must specify which tiers include each capability; place admission in reusable domain owner, not only a router.

#### F04 — EXISTING critical lifecycle: receipt commit causes unrecoverable webhook retry loss

`webhooks.py:174-200` treats any existing event ID as duplicate. `:329-332` commits the received event **before** dispatch. If processing raises/crashes after this commit, a legitimate retry is acknowledged duplicate although no business effect committed. In addition, an early webhook before external-reference persistence becomes `unmatched`; retries cannot reactivate it. No pending/failed receipt claim/retry state exists, and reconciliation only examines pending activations, not accepted subscriptions. Accepted via transaction/control-flow tracing. Keep the **existing BillingWebhookEvent row** as the durable receipt/work item: distinguish received/processing/applied/retryable/rejected/unmatched, lease owner/deadline and retry timestamp; no extra queue required. On duplicate event ID, load the existing row, compare stored payload SHA-256 to the authenticated delivery, and return duplicate only after the effect is terminally applied. A mismatched digest is a conflict/quarantine/alert, never normal replay. Resume pending work under a lease, with safe normalized provider/internal object references sufficient to re-fetch after restart (current hashed summary alone is not enough). Business effect and applied status should commit atomically under idempotency; dedupe must mean effect already applied, not merely event seen.

Exact crash sequence confirmed in source: `process_razorpay_webhook:320-332` inserts/commits a row whose `processed_at` remains NULL; process dies before `:333-344`; retry `_record_event:192-197` hits `ON CONFLICT DO NOTHING`, unconditionally rolls back and returns None; `:327-328` returns duplicate. Neither `processed_at` nor `payload_sha256` is read by that branch. `reconciliation.py:125-129` scans only PendingActivation, so this cannot repair a lost renewal/cancellation on an existing BillingSubscription. There is **no duplicate digest comparison anywhere in this handler**, although the hash is stored.

#### F05 — EXISTING high: current catalog rewrites renewal entitlement and can double-grant a paid period

`service.py:207-209,235-239` fetches templates from the **current** global revision and includes that revision in per-subscription/per-period idempotency. `BillingSubscription` stores no purchased revision. Change revision then accept another active event for the same period: a second grant bundle with a new key is issued and sums with the old one. Even a normal next renewal silently changes purchased terms. Pending payment settling after revision change is rejected (`activations.py:121-122`) instead of honoring its frozen quote. Accepted. Freeze immutable offer revision/benefit bundle/price terms on the agreement; issuance key must be paid entitlement period/effect identity, independent of mutable published catalog revision. An intentional tier change needs an explicit effective-dated transition, never a catalog deployment.

#### F06 — EXISTING high: funded quote is not what base subscription sends or grants

`service.py:482-508` resolves base+credit with distinct private refs and quote total; `api/billing.py:574-581` sends **only base `price_ref`**. Razorpay create payload has only `plan_id`, total_count, notification and notes (`razorpay.py:168-182`), with no credit component. Catalog plan templates never grant audit credits. Configuring margin/provider references can make a funded purchase available, but the separately quoted credits neither reach a second charge/agreement nor a credit grant. Accepted source mismatch; actual provider charges not exercised. Need one frozen billable offer matching provider plan and exact entitlements; do not sell funded mode until complete charge/grant parity is verified.

#### F07 — EXISTING high: Payment Links and Payment IDs are conflated

Adapter creates `/payment_links` and persists its entity ID as `external_payment_id` (`razorpay.py:224-258`, `idempotency.py:251-257`). Webhook parses `payload.payment.entity.id` from `payment.captured` (`webhooks.py:137-163`), then equality-matches pending external_reference (`:213-221`). A payment link's `plink_…` does not equal the payment's `pay_…`; legitimate topup capture is unmatched. Config lacks `payment_link.paid` (`billing_contracts.py:65`). Accepted with current official docs: https://razorpay.com/docs/webhooks/payment-links/ and https://razorpay.com/docs/payments/payment-links/subscribe-to-webhooks/ describe Payment Link-specific paid events and separate link/payment entities. Manual link fetch recovery is not a webhook fix; paid-at evidence also must be translated from actual provider schema, not invented mocks.

#### F08 — EXISTING high: usage API arithmetic contradicts reservation ledger; expired/revoked grants inflate balance

Ledger converts a billed attempt into release+debit (`ledger.py:330-398`), so outstanding is **reservation − release**. Usage projection subtracts debit again (`reads.py:204-211`). For reserve=3/release=1/debit=1, two units remain reserved but API reports one, inflating available balance. Source-function probe reproduced this. Separately `account_usage` discards revocations (`reads.py:305`), `_usage_grant_rows` includes every historical/future/expired/revoked grant (`:218-241`), and `_usage_item` sums them all (`:272-283`): effective expiry is displayed but never used to exclude inactive credit. Conversely `ledger.consumable_usage:499-526` subtracts **all-time** debits from only currently active grants, producing wrong/negative balances after period turnover. Accepted: three competing accounting read implementations. Reuse one canonical active per-grant ledger aggregation for reads and reservations; return historical totals separately. Occupancy/rate usage currently returns unknown rather than actual counts (`reads.py:257-270`) despite enforcement queries already existing.

#### F09 — EXISTING high: no active grant means unlimited occupancy/manual BYOK work

`enforcement.py:304-315` maps missing capability to `allowance=None`, then skips limit rejection. `:433-445` permits manual audits for missing billing link or missing manual-run grant. This is explicitly documented pre-commercial compatibility, not fail closed. After last grant expiry/removal the resolver drops the key, so restrictions disappear. BYOK bypasses funded admission (`funded_admission.py:215-216`), and healthy BYOK selection requires no paid access proof (`credentials.py:292-303`). Public baseline mitigates normal project/prompt cases but does not grant manual-run limits. Accepted. Distinguish explicit unlimited DB policy from absent/zero allowance; separate product access from funding selection. BYOK should bypass model spend only, unless an explicit approved override also changes commercial limits.

#### F10 — EXISTING high: monitored URL quota multiplies by sponsored workspace count

Account resolver projects its entire URL allowance to **each** sponsored workspace (`entitlements/service.py:213-255`). Selection locks/counts **one workspace**, not sponsor account (`site_health/selection.py:483-527`). With two workspaces a 150-URL account can select 150 in each, contradicting account-wide baseline/catalog wording and project/prompt accounting. Accepted, not a concurrency race: the scopes disagree. Count URLs across account-linked workspaces under account capacity serialization, retain runtime rows as operational projections; or explicitly approve workspace-scoped commercial units and price them. Recommendation: all purchased occupancy is account-wide.

#### F11 — EXISTING high: subscription status and elapsed time do not consistently revoke execution

`service.py:99-102,165-176,325-329` only revokes on cancelled/expired **without a future period end**. Halted maps to unpaid and paused to past_due (`billing_contracts.py:85-95`), but neither masks/revokes still-valid plan grants. No implemented grace deadline consumes `past_due_grace_days`. Immediate cancellation with a future current_end is treated as access-through-end regardless of provider cancellation semantics. `live_base_subscription` checks status membership only (`service.py:665-676`); pending/trialing/past_due count as live, and paid-through time is not checked. Accepted absence of specified state policy, not proof all provider cancellation events are wrong.

Site Health worker's pure guard accepts any positive `monitored_url_limit` and does not check `resolved_valid_until` (`site_health/entitlements.py:169-193`, `task_guards.py:106-131`); lazy refresh only occurs on selected planner/read/mutation paths. A natural expiry without a webhook/refresh leaves queued analysis permitted. Positive-to-smaller-positive downgrade also lets all previously monitored rows continue; no account quota selection/parking strategy exists. `runtime_policy_is_current:77-87` compares limits only and skips provenance/validity refresh when equal. Accepted; expired positive runtime source-function probe returned allowed. Define grace/suspension/paid-through policies, refresh/time-check before new I/O, preserve historical evidence, and deterministically block excess new work.

#### F12 — EXISTING high: ambiguous events overwrite state and incomplete active records grant indefinite access

`accept_subscription_event` only rejects strictly older **nonzero** versions (`service.py:143`); equal timestamps with different statuses and unversioned updates both apply. Probe reproduced same-version halted then active restoring active. Fetch DTO often defaults missing version to 0 (`razorpay.py:96`), webhook falls back to event creation timestamp (`webhooks.py:125-128`): these are not a common monotonic provider version. Known subscription events skip plan/amount validation; first activation allows missing price_ref/account/intent metadata (`activations.py:112-147`, tested absent price_ref). Active event requires period_start but not period_end for issuance (`service.py:203-205,240-243`), allowing an unbounded `valid_until=None` plan grant. Accepted. Require complete bounded authoritative settlement evidence; compare state with provider fetch on ambiguous ordering; never assume second-resolution timestamps are unique transition sequence numbers.

#### F13 — EXISTING high: uncertain provider creation is not recoverable; sweep claims are not durable

Intent commits before provider I/O, correctly. But retryable creation failure leaves pending with no external reference (`idempotency.py:443-452`); metadata lookup/list recovery is absent. Reconciliation immediately returns no provider record when no reference (`reconciliation.py:152-160`), eventually abandons it after 24h (`:219-228`), even if remote creation succeeded. Incoming webhook also matches only external_reference, not the supplied opaque intent note. Accepted. Add provider-supported idempotency where documented, otherwise bounded lookup by opaque intent/ref and reconciliation of uncertain outcomes; never automatically create a replacement charge on a timeout.

`_claim_batch:118-149` uses SKIP LOCKED but commits without claim owner/lease/next-attempt update; concurrent sweep callers can fetch the same batch after the lock releases. Always selecting oldest created rows can starve later rows if the first batch stays pending. Existing active subscriptions are never reconciled, there is no scheduled sweep, and auth/permission 4xx is nonretryable then treated as missing in `_settle_claim:213-228`. Do not abandon a financial intent because credentials are broken. Accepted control-flow/scoping defects. Add durable lease/backoff, bounded cursor, failure categories, active lifecycle/invoice/refund reconciliation, and alerts.

#### F19 — Concurrency hypotheses: accepted risks vs claims not established

#### F20 — EXISTING high contract defect: ledger replay does not verify the requested identity; no refund entry exists

`ledger.py:217-236` looks up only `(billing_account_id, idempotency_key)`. 3. Worker preflight: recheck entitlement, expiry/revocation and allowed funding route, verify live lease/cancellation, freeze actual route and call ID, ensure sufficient hold, write dispatch receipt, commit, then I/O. Content currently freezes provider at enqueue but builds the client from current config, so record/check the actual dispatch route; do not price a new endpoint as the frozen old provider.
4. Receive: normalize/store usage even if output is empty, schema parsing fails, output is discarded, or lease is lost. Lease fencing controls **result publication**, not destruction of paid-attempt evidence. Settle exactly once per real dispatch; a stale completion must never bill the successor's call identity.
5. Known usage: calculate internal credits with frozen conversion/rounding rules, atomically debit allocations and release unused reserved units, then publish outcome/retry. No-provider fallback and pre-I/O configuration/tool failures use no model tokens; release their unspent hold rather than charging a fictional provider attempt.
6. Retry: each actual call has a new dispatch ID, evidence and funding check; do not reuse a previous debit as the retry charge. Main policy must say which paid failed attempts consume customer credits versus platform-funded compensation. Preserve provider expense regardless. Current audit policy bills timeouts; do not silently apply it to token-metered unknown calls.
7. Cancel/terminal: queued, never-dispatched work releases all holds. In-flight cancellation stops future work and result publication but cannot prove provider cancellation or zero spend. Release only uncommitted future-call hold; settle known in-flight usage and retain uncertain hold until bounded reconciliation. Operator compensation appends a linked refund, never deletes usage or replenishes twice.
8. Recovery: reclaim expired leases without erasing dispatch receipts. Reconcile success/lost-response/timeout with provider lookup where actually supported; otherwise apply the explicitly approved bounded uncertainty policy (hold deadline, conservative debit cap or platform absorption). Never invent exact tokens. No exactly-once HTTP promise without provider idempotency; duplicate I/O must still have distinct receipts and bounded exposure.
9. Nested/multi-step budget: current tools do not enqueue Content. If a bounded Agent tool later does so, require a root run budget and typed child Content FK/provenance; reserve the aggregate worst-case model/tool/retry cost, not an independently renewable budget per step. Transfer/split existing hold allocations to child execution atomically (zero additional account reservation), or let the parent budget authorize the child-owned reservation without duplicating a parent hold. Debit each actual provider dispatch exactly once at the leaf: parent usage is an aggregation, never a second debit for the same Content call. Hard-stop before an unbudgeted call. No cross-product generic wallet or arbitrary execution graph framework.
10. Streaming/future tools: no new scope now. If added later, reserve before opening stream; persist final/partial usage on abort, retain unknown after disconnect, and meter each paid model/tool call with its own ordinal. Existing DB evidence reads are not token charges; their prompt inclusion is captured in the narration's input tokens.
